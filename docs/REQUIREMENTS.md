# 语音输入法 OpenType — 议题要求

## 项目目标

开发一个语音输入法产品，帮助用户提高文本输入效率。要求较好地平衡**准确度、易用性、响应速度、成本**等关键因素。

---

## 评审规则

| 维度 | 权重 | 说明 |
|------|------|------|
| **作品完整度与创新性** | 40% | 产品设计合理性、功能完整度、交互流畅度、是否新颖有创意 |
| **开发过程与质量** | 40% | 架构清晰度与合理性、代码健壮度（逻辑、规范、可读性）、PR 数量与质量、commit 分布合理性 |
| **演示与表达** | 20% | demo 视频清晰完整度，是否清晰完整表达作品功能和效果 |

---

## 开发周期（3 日）

- **第 1 天**：创建 GitHub 仓库，完成报名表单提交，开始开发
- **第 2 天**：持续迭代，按要求提交 PR 和 commit
- **第 3 天**：完成作品，确保资料提交无误：公开代码仓库、demo 视频、README 文档

---

## 作品提交要求

### 一、提交内容

1. **公开的 GitHub / Gitee 仓库**（提交截止后可公开访问）
2. **Demo 视频**（上传至可访问平台，如 bilibili / 云盘，链接放在 README 显眼位置）
3. **README 文档**

### 二、作品有效性

1. 作品需符合议题方向，确保自主完成无抄袭
2. **全周期持续交付**：从议题发布起保持持续的 PR 和 commit 记录；仅最后一天一次性导入所有代码的作品将视为**无效**
3. 所有 commit 时间戳必须落在批次的开始与截止时间内
4. 以下情形视为无效：
   - PR 描述空白或与实际代码变更严重不符
   - 引用第三方库/框架，未在 README 中列明依赖且未说明原创功能部分
   - 复用自己过去的代码片段，未在 PR 描述中注明来源

### 三、PR（Pull Request）提交规范

1. 每个 PR **只做一件事**：只实现或修改单一功能
2. 鼓励尽可能小、粒度尽可能细的 PR；大功能应拆分为多个独立 PR 分步提交
3. PR 标题与描述需清晰完整：
   - **标题**：一句话说明本 PR 新增/修改了什么
   - **功能描述**：说明该功能的作用与使用方式
   - **实现思路**：简要说明技术选型或核心实现逻辑
   - **测试方式**：如何验证该功能正常运行
4. PR 合并后，主分支代码需保持可运行状态

### 四、Demo 视频要求

1. 用声音完整讲解、展示作品主要功能和效果，覆盖核心模块
2. 上传至可访问的外部平台（bilibili / 云盘等），链接放到 README **显眼位置**

### 五、其他要求

1. 多人组队：每队仅提交一个仓库地址；队员均须使用各自账号提交 commit，PR 清晰描述各自分工
2. 多模块项目：提交至同一仓库的不同子目录（如 `/frontend` 与 `/backend`）分别管理
3. 代码仓库需在开题后创建
